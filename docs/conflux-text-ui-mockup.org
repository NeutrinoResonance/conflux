A user cancels a running job, the API returns 200, and the row briefly says
=cancelled=. A few milliseconds later it sometimes changes to =completed= and the

The cancellation code uses a conditional update, but completion does not:

// complete.ts
await db.query(`
  UPDATE jobs
     SET state = 'completed', result = $2

`, [jobId, result]);
#+end_src

** ASSISTANT · 9:15 AM — diagnosis verified                       :assistant:

The completion update is overwriting a successful cancellation.

The cancellation statement protects itself from invalid starting states, but the
completion statement accepts every state. This ordering produces the bug:

1. Worker begins its completion path.
2. The API changes =running → cancelled= and returns 200.
3. The worker's unconditional update changes =cancelled → completed=.
4. The publisher sees =completed= and emits the result.

I reproduced that sequence 31 times in 1,000 forced interleavings against the
repository snapshot. I would fix it by making completion a compare-and-set from
=running= and treating a zero-row update as “completion lost the race.” No files
have been changed.
